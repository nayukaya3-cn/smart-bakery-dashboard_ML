# スマートパン屋農家 スマート化ダッシュボード（日→週→月のルーティン版）

農業法人「スマートパン屋農家」の **経営・マーケティング・プロダクト** を、
**毎日3分 記録する → 毎週10分 問題を見つける → 毎月30分 打つ手を決める** のリズムで少しずつ進化させるダッシュボード。
講義「多分野データ解析実践演習Ⅰ」第1〜3回（DSとは／DSプロセス／DS設計）を「学ぶ」ページに、
最適化・因果・ベイズの発展を「深掘り」ページに置いている。先行事例：[work-diary-trouble-dashboard](https://github.com/nayukaya3-cn/work-diary-trouble-dashboard)。

## 起動

```bash
pip install -r requirements.txt
streamlit run app.py
pytest -q          # 計算部品の検証（期待値は人が先に決めたもの）
```

ページは URL で直接開ける：`http://localhost:8501/nippo`・`/shuukei`・`/tsuki`

## 毎日のルーティン（主軸）

| いつ | /コマンド | 3段構え | 機械がすること | 人がすること | 残るもの |
|---|---|---|---|---|---|
| 毎日（3分） | `/nippo` | ① 記録する | KPI計算、直近4回の同じ曜日の中央値と比べて「要確認／よい変化／いつも通り」を提案、商品別の廃棄・売切れ | 日報（天気・客数・労働時間・SNS投稿・メモ）と商品別の製造数・販売数を入れる。提案に **OK／直し** と **ひとこと（なぜか）** | 日報・販売表・確認 |
| 毎週（10分） | `/shuukei` | ② 問題を見つける | 現状（As Is）とあるべき姿（目標）の差＝問題（Issue）を差の大きい順に並べる。商品の地図（販売数×廃棄率） | 取り組む問題を選び、**課題（Action）** を「〜を明らかにする／改善する」で書く | 今週の課題・Markdown週報 |
| 毎月（30分） | `/tsuki` | ③ 打つ手を決める | 商品ごとの廃棄率を **ベイズ推定（Beta(1,1)・90%区間）**、P(前月より悪化)、優先度の目安 | **準備度** を答え、**順番・打つ手・担当（役割）・期限** を決める。3領域の **ロジックモデル** を更新 | 決定（翌月のふりかえりに使う） |

### 3つの領域とKPI

| 領域 | KPI | あるべき姿（サイドバーで変更） |
|---|---|---|
| 💴 経営 | 売上、粗利率（作った分の原価で計算）、人時売上（売上÷労働時間） | 月125万円、58%、2,000円/時間 |
| 📣 マーケティング | 1日あたり客数、客単価、新規会員（30日換算）、再来店率 | 780円、25人/30日 |
| 🥐 プロダクト | 廃棄率（廃棄数÷製造数）、売切れ（売り逃しの可能性）、自家原料の売上比率 | 10%以下 |

週・月の比率は「日ごとの率の平均」ではなく、合計から計算し直している（テストあり）。

### 優先度の目安（/tsuki）

```
優先度 = 廃棄金額 × (1 − 準備度/3) × (1 + w × max(0, P(前月より悪化) − 0.5))
```

準備度：0 手がない／1 担当は決まっている／2 手順が書いてある／3 試して効いた（3なら0）。
**機械が出すのは提案順まで。順番を決めるのは人**（入れ替えた理由を残す）。前月の手と今月の数字を並べるのは **前後関係であって、効いた証明ではない**。

## データと保存先

| データ | 足した日報・決定 |
|---|---|
| 架空サンプル（2026年4月〜10月21日、水〜日営業、商品6種、会員160人） | ブラウザのセッション内だけ（CSV/Markdownで保存可） |
| **手元のファイル** `data/raw/` | `data/raw/` に保存（`.gitignore` 済み）。毎日使うのはこちら |
| CSV をアップロード（一時） | セッション内だけ |

```
data/raw/daily.csv               日報：日付,天気,最高気温,客数,労働時間,SNS投稿,イベント,メモ
data/raw/sales.csv               販売：日付,商品,製造数,販売数,廃棄数
data/raw/members.csv             会員：会員ID,年代,性別,地区,認知経路,初回来店,来店回数,最終来店（氏名・連絡先は入れない）
data/raw/products.csv            商品マスタ：商品,区分,単価,原価,自家原料比率,販売開始（初回はサンプルの商品マスタを置く）
data/raw/routine/checks.csv      毎日：機械の提案への OK／直し・ひとこと
data/raw/routine/weekly.csv      毎週：選んだ問題と課題（Action）
data/raw/routine/monthly.csv     毎月：準備度・人が決めた順位・打つ手・担当（役割）・期限
data/raw/routine/logic.csv       毎月：3領域のロジックモデル
data/raw/routine/design.csv      第3回：DS設計シート
```

サンプルには、深掘りページで「見抜けるか」を試すための構造を仕込んである：
SNS投稿の真の効果は客数 +8%（ただし投稿は週末に多い）、製造数は「同じ曜日の販売の移動平均×1.12」のルール（雨の日に廃棄が増える）、売切れの日の販売数は需要より小さい（打ち切り）。
サンプルは `python -c "import bakery_core as C; C.write_sample()"` で作り直せる（乱数の種は固定）。

## 安全の約束

- 実データは **手元で** `streamlit run` する。Streamlit Community Cloud 等の公開サーバーには架空サンプルだけを置く。
- 生データ・記録は `data/raw/`（`.gitignore` 済み）。`.claude/settings.json` で `Read(./data/raw/**)` を deny（人の注意ではなく設定で防ぐ）。
- 会員台帳に氏名・電話番号を入れない。それでも「地区×年代×性別」で特定されうるので、外に出す前に `/kai3` の k-匿名性で確かめる。
- 日報のメモにお客さま・取引先の名前を書かない（/nippo で人名らしき語を警告）。担当は名前ではなく役割で書く。
- 発注・シフト確定・SNS投稿は人が行う。機械が出すのは提案と順番の目安まで。
